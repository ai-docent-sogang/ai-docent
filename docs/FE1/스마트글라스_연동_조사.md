# 스마트글라스 SDK를 어디에 넣는가 (조사, 2026-11-18)

작성 2026-11-18. 웹 출처의 확인일은 모두 2026-11-18이다. 저장소는 읽기만 했다.

## 결론 (세 줄)

1. 서버(`/ws/live`)는 바꾸지 않는다. 글라스 SDK는 **폰 동반 앱**에 들어간다. 지금 카메라와 마이크를 서드파티에 여는 상용 글라스(Meta, Mentra, Android XR, Brilliant)는 모두 폰 앱이 블루투스로 입출력을 받는 구조다. 글라스 안에서 직접 WS를 여는 경로(a)는 확인된 것이 없다.
2. 동반 앱은 폰 웹(`static/live_conversation.js` 자리)이 하는 일을 네이티브로 똑같이 한다. 마이크를 16kHz PCM16으로 바꿔 계속 보내고, 3초마다 JPEG 프레임을 보내고, 24kHz PCM을 재생하고, `interrupted`가 오면 재생을 즉시 멈춘다.
3. 12/1 권고: 시연은 (c) 최소 대안으로 한다. 폰 웹 handsfree에 블루투스 이어폰·마이크(글라스를 블루투스 헤드셋으로만 써도 된다)와 폰 카메라를 붙인다. SDK 연동(b)은 12/1 이후로 미룬다. 1순위 후보는 국내에서 살 수 있는 Ray-Ban Meta와 Meta DAT(iOS)다.

## 3. SDK를 넣을 자리

### 서버가 기대하는 것 (변하지 않는 기준)

`server/live.py`와 계약서 기준이다. 텍스트 JSON과 바이너리 PCM을 섞은 WebSocket 연결 하나를 쓴다.

- 보낼 것: 첫 메시지 `{"mode":"handsfree","session_id":...,"profile":...}`, 16kHz 모노 PCM16을 끊김 없이 보냄(조용할 때도), 3초마다 `{"type":"frame","jpeg":"<base64, 가로 최대 768px>"}`, 필요할 때 `{"type":"text"}`.
- 받을 것: 24kHz PCM16 재생, `heard`, `said`, `interrupted`(재생 즉시 중단), `turn_complete`, `artwork`, `comparison`, `reconnecting`, `reconnected`, `error`.
- 그 전에 `POST /api/session`으로 `session_id`를 받는다.

글라스 쪽에 이 형식을 맞추면 서버 코드는 바뀌지 않는다. 키는 서버에만 있으므로(AGENTS.md) 글라스든 폰 앱이든 Gemini에 직접 붙지 않고 `/ws/live`에 붙는다.

### 누가 무엇을 하는가

| 할 일 | 폰 웹(지금) | (a) 글라스가 직접 WS | (b) 폰 동반 앱 + 글라스 SDK | (c) 블루투스 이어폰·마이크 + 폰 카메라 |
| --- | --- | --- | --- | --- |
| 마이크 → 16kHz PCM16 | AudioWorklet(`live_mic_worklet.js`) | 글라스 앱 | 동반 앱. Meta는 8kHz HFP라 16kHz로 올려서 보냄. Mentra·Android XR은 16kHz 그대로 | 폰 웹 그대로. OS가 블루투스 마이크를 입력으로 잡음 |
| 카메라 → JPEG 3초마다 | `<video>` → canvas → JPEG | 글라스 앱 | 동반 앱. Meta는 저fps 스트림에서 프레임을 골라 JPEG로 만들거나 `capturePhoto(.jpeg)`. 가로 768px 이하로 줄이고 base64로 보냄 | 폰 웹 그대로(폰 카메라) |
| 24kHz PCM 재생 | `live_player.js` | 글라스 앱 | 동반 앱이 폰에서 재생하고, OS가 글라스 스피커로 보냄. Halo만 앱이 직접 PCM을 넣는데 8/16kHz라 내려서 넣어야 함 | 폰 웹 그대로. 소리는 이어폰으로 나감 |
| `interrupted` 시 재생 중단 | 플레이어 큐 비우기 | 글라스 앱 | 동반 앱의 플레이어 큐 비우기 | 그대로 |
| WS·재연결·자막 | 브라우저 | 글라스 앱 | 동반 앱 | 그대로 |
| 가능 여부 | 동작 중 | 조사한 기기 중 확인된 경로 없음 | 가능(개발자 프리뷰) | 지금 가능, 코드 추가 없음 |

(a) 글라스 직접 연결: Meta 글라스 위 Web Apps는 카메라와 마이크를 쓸 수 없다고 문서에 적혀 있다[M4]. Halo는 BLE와 Lua만 있다[B1]. Mentra Live는 Wi-Fi가 있지만, 서드파티 코드가 글라스 안에서 WS를 열 수 있는지는 확인하지 못했다(확인 필요). 지금은 고려하지 않는다.

(b) 폰 동반 앱: 현실적인 연동 방식이다. SDK는 동반 앱 안에 들어간다. 이 앱이 `static/live_conversation.js`의 네이티브판이 된다.

(c) 최소 대안: 코드를 추가하지 않는다. 할 일은 `glasses/`에 시험 기록을 남기는 것뿐이다. Ray-Ban Meta도 블루투스 헤드셋으로만 쓰면 이 경우에 들어간다. 이때 카메라는 폰 카메라를 쓴다.

### 저장소 안의 구분

- `glasses/`(FE2): 후보 비교표(이 문서의 2장), (c) 시험 기록, (b)를 할 때의 동반 앱 프로젝트(예: `glasses/ios/` Swift + DAT). 동반 앱은 폰 웹과 같은 메시지 형식을 쓴다. 기준 문서는 `docs/api.md`의 `/ws/live` 절과 이번 handsfree 계약이다.
- 서버: 바꿀 필요가 없다. 다만 아래 두 가지는 선택 사항이므로 BE1·FE1 합의 대상으로 둔다.
  - 8kHz 입력: 클라이언트가 16kHz로 올려 보내면 서버 변경은 없다. 서버가 입력 샘플레이트를 받게 하려면 `docs/api.md`를 먼저 고쳐야 한다. 지금은 필요 없다.
  - 에코: `docs/api.md`는 "에코 처리 없음(이어폰 사용 전제)"라고 적고 있다. 글라스 스피커는 귀를 막지 않는 오픈형이라, 자동 음성 감지(handsfree)에서 답변 소리를 다시 받아 스스로 끼어들 위험이 있다(추정). 동반 앱은 OS의 통화용 에코 제거 경로(iOS voice processing, Android `VOICE_COMMUNICATION`)로 녹음해야 한다. 실제 효과는 기기로 시험해야 한다(확인 필요).

## 4. 12/1까지의 권고

권고: 12/1 시연은 (c)로 한다. 폰 웹 handsfree에 블루투스 이어폰·마이크와 폰 카메라를 붙인다. 글라스는 "같은 `/ws/live`에 동반 앱으로 붙는다"는 구조도와 이 표로 설명한다. Ray-Ban Meta를 구할 수 있으면 블루투스 헤드셋으로만 연결해 보여 준다.

이유
- 개발계획서가 글라스를 12/1 범위 밖으로 두었다(64줄). 11/13 결정도 폰 웹 우선이다.
- (b)를 하려면 2주 안에 새 네이티브 앱(Swift/Xcode, 애플 개발자 서명, Meta AI 앱 등록)을 만들어야 한다. 그런데 DAT의 오디오 스트리밍과 카메라 캡처는 실험 기능이다[M2].
- Meta 마이크는 8kHz HFP라[M1] 지금 폰 마이크보다 받아쓰기 품질이 떨어질 수 있다. 이것도 시험 대상이 늘어나는 이유다.
- 오픈형 스피커의 에코는 handsfree의 자동 음성 감지와 부딪힐 수 있다. 기기 없이 미리 검증할 수 없다.
- (c)는 서버와 화면 코드를 바꾸지 않는다. 아이폰 Safari에서 블루투스 마이크가 입력으로 잡히는지만 확인하면 된다.

12/1 이후 (b)의 1순위는 Ray-Ban Meta Gen2와 DAT iOS다. 국내에서 690,000원에 정식으로 살 수 있고[M6], 아이폰을 지원하고, 카메라와 마이크가 열려 있기 때문이다. 2순위는 Mentra Live다. 16kHz PCM과 JPEG를 바로 주고 React Native도 지원하지만, 미국 배송만 된다는 정보가 있다(확인 필요). Android XR 글라스는 안드로이드 폰이 필요하고 12/10 출시라 시연 일정에 맞지 않는다.

3. 구매한다면 어떤 모델을 언제까지 살 것인가. (c)만 하려면 11/25 기기 테스트 주간 전에 받아야 한다.

5. 아이폰 기준을 유지할 것인가(Meta·Mentra 가능), 안드로이드도 허용할 것인가(Android XR 가능).
6. "AIVY 실기기"(역할 가이드 323·366·393줄)가 무엇을 가리키는가.
