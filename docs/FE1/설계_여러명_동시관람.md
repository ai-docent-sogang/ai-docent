# 설계: 12/1 시연에서 여러 명이 동시에 쓰기

작성: FE1 김도혁, 2026-11-19. 상태: **제안, 팀 확인 전.**

## 먼저 — 전제가 틀렸다

11/13에 "여러 관람객 동시 접속은 11/18 범위 밖, 12/1 범위로 미룬다"고 정했고, 그 뒤 문서마다 **"한 번에 한 명만"** 으로 적어 왔다([통합 인터페이스 60줄](../11-18_통합_인터페이스.md), [결정사항 11/13](../결정사항.md)).

**코드를 확인해 보니 이미 여러 명이 된다.** 11/19에 가짜 Gemini로 두 명을 동시에 붙여 봤다.

```
v1: session_id=65a605f9… · 받은 답=['answer for visitor1']
v2: session_id=b7df9f50… · 받은 답=['answer for visitor2']

관람 두 개가 서로 다른 session_id를 받았나: True
답이 섞이지 않았나: True
```

이유는 설계가 처음부터 관람별로 갈라져 있었기 때문이다.

| 관람별로 갈린 것 | 어디 |
| --- | --- |
| 대화 상태(지금 작품, 들은 말, 재개 핸들 등 16가지) | `live()` 함수 안의 `state`. 연결마다 새로 만든다 |
| 관람 기억(프로필, 본 작품, 쓴 비교) | `session.py`의 `_sessions[session_id]` |
| 재개 핸들 | `live.py:189` `resume_store[session_id]` |
| 지금 붙어 있는 연결 | `live.py:192` `active_connections[session_id]` |
| 관람 기록 | `visit_log` 객체를 관람마다 하나 만든다. `visit_id`도 따로 |

공유하는 것은 **읽기만 하는 것**뿐이다(작품 CSV, 비교쌍 CSV, 설정값). 그래서 서로 간섭할 수 있는 자리가 없다.

**그러니까 "동시 접속 기능을 만든다"는 일은 없다.** 대신 아래 세 가지가 진짜 할 일이다.

---

## 1. 무엇이 필요한가

### 되어야 하는 것

- 12/1 시연에서 **심사위원·멘토 여러 명이 각자 폰으로** 동시에 쓴다.
- 한 명이 끊기거나 끝내도 다른 사람에게 영향이 없다.
- 시연 중에 **지금 몇 명이 붙어 있는지** 우리가 볼 수 있다.

### 숫자로 정해야 하는 것

- **동시 몇 명을 목표로 하나.** 지금 아무도 정하지 않았다. → 아래 3장에서 제안한다.
- 관람 한 번에 Gemini 토큰 **약 5,400개**(질문 2개·55초, 11/18 실측 1회). 동시 인원에 비례해 늘어난다.
- 응답 지연 1.2~2.9초. 동시 인원이 늘어도 유지되어야 한다(서버가 중계만 하므로 영향이 작을 것으로 본다. **확인 필요**).

### 제약

- 팀 5명, **11/25에 기능 동결**, 오늘 11/19 → **새로 만들 시간 7일.**
- Gemini API 키 **하나를 전원이 나눠 쓴다.** 11/18에 한 번 크레딧이 소진돼 모든 확인이 멈춘 적이 있다.
- 서버는 노트북 한 대에서 `uvicorn` 하나로 돈다. 여러 대로 늘리는 계획은 없다.

## 2. 진짜 할 일 세 가지

### 가. 세션이 영원히 안 지워진다 (가장 큰 것)

관람 기억은 폰이 **END VISIT을 눌러 `/api/session/{id}/end`를 부를 때만** 지워진다(`static/app.js:407`, `server/session.py:64`).

**그런데 버튼 없는 대화에서는 관람객이 END VISIT을 누르지 않는다.** 그냥 폰을 주머니에 넣고 떠난다. 그러면:

- `_sessions[session_id]`가 **서버 메모리에 영원히 남는다.** 지우는 코드가 없다(`server/live.py`에 `end_session` 호출이 없다 — 확인).
- `resume_store`는 2시간 만료가 있지만 **누군가 `saved_resume()`을 부를 때만** 치운다. 아무도 다시 안 붙으면 안 치운다.

12/1 시연 한 번에 관람 30번이면 몇 MB다. **터지지는 않는다.** 하지만 지금은 **몇 개가 쌓였는지 볼 방법도 없다.**

### 나. 지금 몇 명이 붙어 있는지 모른다

서버 로그에 연결/종료 줄이 찍히지만 **시연 중에 터미널을 읽을 수 없다.** 개발계획서는 운영 페이지(대시보드)를 12/1 포함 범위로 적어 뒀는데 아직 없다.

시연에서 "지금 세 명 붙어 있고 다 정상"을 1초에 확인할 방법이 필요하다.

### 다. Gemini 쪽 동시 한도를 모른다

Live 세션 하나당 소리와 사진을 끊임없이 올린다. **동시에 몇 개까지 되는지 우리가 확인한 적이 없다.** 공식 문서의 한도도 확인하지 않았다.

**이게 제일 위험하다.** 시연 중에 네 번째 사람이 붙으면서 전부 끊기는 것이 최악이다.

## 3. 어떻게 할까 — 고른 길

### 목표 인원: **동시 3명**

근거다. 심사위원이 여럿이어도 동시에 말을 거는 사람은 보통 한두 명이다. 3명이면 여유가 있고, 그 이상은 Gemini 한도를 모르는 상태에서 약속할 수 없다.

### 가. 세션 청소 — 세 가지 길

| | 방법 | 복잡도 | 12/1까지 |
| --- | --- | --- | --- |
| A | **Live 연결이 끝날 때 세션도 지운다** | 가장 낮음 | 10분 |
| B | 오래된 세션을 주기적으로 치운다(TTL) | 중간 | 40분 |
| C | 세션을 파일·DB에 옮긴다 | 높음 | 하루 넘음 |

**A는 안 된다.** 연결이 끊기는 것이 정상인 설계다(10분마다 Gemini 연결이 바뀌고, 폰 네트워크도 끊긴다). 끊길 때 세션을 지우면 **다시 붙었을 때 앞 대화를 잃는다.** 지금 제일 공들인 기능을 망친다.

**C는 버린다.** 개발계획서가 "계정, 장기 이력 저장"을 12/1 **제외**로 적었고, 개인정보 원칙도 "세션 기억은 세션이 끝나면 폐기"다. 파일로 옮기는 것은 그 원칙과 반대다.

**→ B를 고른다.** 재개 핸들과 같은 시계(2시간)를 쓴다. 이미 `resume_store`에 2시간 만료가 있으니 같은 기준이면 설명이 하나로 끝난다. 2시간 넘게 아무것도 안 온 관람은 떠난 것으로 본다.

**맞바꾼 것**: 관람객이 2시간 안에 돌아오면 이어진다. 2시간 1분 뒤에 돌아오면 새 관람이 된다. 전시 관람이 2시간을 넘는 일은 드물고, 넘더라도 "앞 대화를 잃었다"고 안내하는 길이 이미 있다.

### 나. 운영 페이지 — 가장 작은 것부터

`GET /live/status` 한 개를 만든다. JSON 한 덩이다.

```json
{"active_visits": 3,
 "visits": [{"session_id": "65a6…", "artwork_id": "KHD_SSIREUM",
             "idle_s": 2.1, "gemini_connected": true, "reconnects": 0}],
 "saved_resumes": 5,
 "model": "gemini-3.8-live", "voice": "Kore", "frame_policy": "every"}
```

**세션 ID는 앞 4자만** 보여 준다. 관람객을 식별하는 값이고, 설계상 기록에 남기지 않기로 한 값이다.

폰이 아니라 **우리가 보는 것**이라 화면은 나중에 붙인다. 시연 날은 노트북 브라우저로 이 주소만 열어 두면 된다.

| | 방법 | 12/1까지 |
| --- | --- | --- |
| A | **JSON 한 개** | 30분 |
| B | JSON + 자동 갱신 화면 | 2시간 |
| C | 제대로 된 대시보드(작품 켜기/끄기까지) | 하루 넘음 |

**→ A를 먼저 하고, 시간이 남으면 B.** C는 개발계획서가 포함으로 적었지만 7일에 들어갈 일이 아니다. **팀장 판단으로 범위를 줄이자고 제안한다.**

### 다. Gemini 동시 한도 — 재 본다

**설계로 풀 수 없다. 재 봐야 안다.** 7일 안에 할 일은 이것이다.

1. 공식 문서에서 Live 세션 동시 한도와 분당 한도를 확인한다(아직 안 했다).
2. 가짜 폰 3대를 동시에 붙여 **실제 Gemini로** 한 번 돌린다. 토큰과 지연을 잰다.
3. 결과에 따라 목표 인원을 확정한다. 3명이 안 되면 **시연 대본을 "한 명씩 번갈아"로 바꾼다.**

**비용 주의**: 3명 × 1분이면 대략 토큰 1.6만~2만 개로 어림잡는다(1회 실측에서 선형 추정이라 **거칠다**). 크레딧을 보고 한 번만 돌린다.

## 4. 한도에 걸리면 어떻게 하나

재 보기 전이라 **가정**이다. 확인 뒤에 고친다.

| 생기는 일 | 지금 | 하려는 것 |
| --- | --- | --- |
| 네 번째 사람이 붙는데 Gemini가 거절 | 그 사람 화면에 `reconnecting`이 계속 뜬다. **왜인지 알 수 없다** | 붙기 전에 세어서, 목표 인원을 넘으면 폰에 "잠시 뒤 다시 시도해 주세요"를 또렷하게 보낸다 |
| 한 명이 한도를 다 쓴다 | 다른 사람이 같이 끊긴다 | 12/1 범위 밖. 시연은 우리가 통제한다 |

**받아들이는 한계**: 동시 인원 제한은 **예의상의 안내**다. 서버가 막는 게 아니라 숫자를 세어 알려 주는 것뿐이다. 시연에서 통제되는 환경이라 그 정도로 충분하다고 본다. 공개 서비스라면 다르다.

## 7. 커지면 다시 볼 것

12/1 뒤, 실제 관람객을 받는다면 달라지는 것들이다.

- **서버 한 대**로는 안 된다. 관람 상태가 그 프로세스 메모리에 있어서 서버를 늘리면 관람객이 다른 서버로 갈 때 대화를 잃는다. 상태를 바깥(Redis 같은 것)으로 옮겨야 한다.
- **API 키 하나**로는 안 된다. 한 사람이 한도를 쓰면 전원이 멈춘다.
- **인증이 없다.** 지금은 주소를 아는 사람이면 누구나 붙는다. 12/1 시연은 통제된 환경이라 범위 밖으로 둔 것이다.
- **세션을 메모리에 두는 것**이 개인정보 원칙에는 맞지만, 서버를 다시 켜면 모두 사라진다. 운영에서는 그 맞바꿈을 다시 봐야 한다.
