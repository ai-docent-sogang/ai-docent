# Live API 전환 검토 — 코드로 확인한 부분 (FE1, 2026-11-11)

담당: FE1 김도혁. 측정 도구: [`archive/tools/live/probe_live_audio.py`](../../archive/tools/live/probe_live_audio.py),
[`tools/live/live_relay_spike.py`](../../tools/live/live_relay_spike.py), [`tools/live/fake_browser_live.py`](../../tools/live/fake_browser_live.py).

> 11/23 주: 이 문서가 말하는 `/api/ask`는 폐기했다. 시연 안전망은 `/api/turn`의 마이크 탭 녹음이 맡는다(Live 연결이 실패하면 화면이 그쪽으로 돌아온다).
배경: BE1의 방식 비교 PR #7, FE1의 [응답 시간 측정](../../archive/docs/FE1/FE1_응답시간_측정.md).

## 왜 확인했나

BE1이 Live API로 첫 응답 0.8초(요청-응답은 8.1초), 사실 정확도 10/0/0을 측정하고 "Live 전환 여부는
FE1 음성 처리 작업량과 함께 결정해야 한다"고 남겼다. 다만 BE1의 실험은 질문을 **텍스트**로 보냈다.
FE1에게 중요한 것은 **음성을 넣었을 때**도 되는지, 그리고 폰 브라우저에서 그 경로를 쓸 수 있는지다.
실기기 없이 코드로 확인할 수 있는 것부터 확인했다.

## 확인한 것 ①: Live가 음성을 듣고, 우리 자료로 답한다

합성 음성("Who painted this, and why is the boy crying?")을 16kHz PCM으로 만들어 Live에 보냈다.
실제 관람객 음성을 쓰거나 저장하지 않으려고 맥의 `say`로 만든 소리를 썼다.

| 항목 | 결과 |
| --- | --- |
| 들은 질문 | "Who painted this and why is the boy crying?" — 정확 |
| 답변 | `key_facts`의 회초리·암송 평가 해석을 박물관 해석이라는 단서와 함께 말함 |
| 첫 음성까지 | 1,260 ms |
| 출력 형식 | `audio/pcm;rate=24000` (공식 문서와 일치) |
| 연결 시간 | 2,039 ms (관람 시작 때 한 번만) |

**DB를 거친다.** 작품의 `key_facts`를 시스템 지시문에 넣고 `ASK_INSTRUCTION`을 그대로 썼다.
BE1이 측정한 정확도 10/0/0도 같은 방식이었으므로, Live로 바꿔도 콘텐츠 DB 근거는 유지된다.

엉뚱한 질문을 걸러내는 것도 확인했다. 같은 음성을 **인왕제색도**에 대고 보냈더니 "우는 아이는
이 그림에 없고 자료에도 없다"고 답하고 다른 볼거리를 권했다. 지어내지 않았다.

## 확인한 것 ②: 폰 → 우리 서버 → Gemini 중계가 동작한다

`AGENTS.md`는 클라이언트 코드에 API 키를 넣는 것을 금지한다. 따라서 **폰 브라우저가 Gemini Live에
직접 붙을 수 없고**, 우리 서버가 WebSocket으로 가운데서 음성을 넘겨야 한다. 이게 Live 전환의
가장 큰 구조 변화다. `/api/ask`·`/api/turn`은 요청 한 번에 응답 한 번이지만, Live는 연결을 열어 둔다.

가장 작은 중계 서버를 만들고, 폰처럼 100ms씩 실시간으로 음성을 올리는 가짜 브라우저로 시험했다.

| 항목 | 결과 |
| --- | --- |
| 경로 | 가짜 브라우저 → 우리 서버(WebSocket) → Gemini Live → 서버 → 브라우저 |
| **말이 끝난 뒤 첫 음성까지** | **950 ms** |
| 답변 음성 길이 | 13.7초 (24kHz PCM 658 KB) |
| 받아쓰기 | 정확 |

`/api/ask`의 7,945 ms와 비교하면 **8배 빠르다.** 실시간으로 보내면 모델이 들으면서 처리하므로
텍스트로 보낼 때(1,260 ms)보다도 빨랐다.

## 확인하지 못한 것 — 실기기가 필요하다

아래는 코드로 알 수 없다. 아이폰 Safari에서 직접 해 봐야 한다.

- **마이크를 16kHz PCM으로 실시간 뽑기.** 지금 `static/audio.js`는 녹음이 끝난 뒤 한 번에 WAV로
  바꾼다(`OfflineAudioContext`). Live는 말하는 동안 계속 보내야 하므로 `AudioWorklet`이 필요하다.
  Safari가 지원하지만 우리 코드로 해 본 적이 없다.
- **24kHz PCM 재생.** 받은 소리는 WAV 파일이 아니라 생 PCM 조각이다. `AudioContext`로 이어 붙여
  끊김 없이 재생해야 한다. Safari의 자동 재생 제약(사용자 조작 안에서 시작해야 함)은 이미
  `initAudio()`로 겪은 문제이고, Live에서도 같은 제약이 걸린다.
- **에코.** 스피커로 답변이 나오는 동안 마이크가 그 소리를 다시 듣는다. 이어폰을 쓰면 줄지만
  기기와 함께 확인해야 한다. 지금 흐름은 버튼을 누를 때 답변 음성을 끊어서 피하고 있다.
- **기관 Wi-Fi에서 WebSocket 연결 유지.** 끊김과 재연결은 실제 망에서만 확인된다.

## 작업량 — 솔직하게

Live로 가면 FE1 쪽은 줄지 않고 **바뀐다.** 브라우저 STT·TTS(`static/stt.js`, `audio.js`의 `speak`)는
필요 없어지지만, 그 자리에 다음이 들어온다.

- `AudioWorklet`으로 마이크 실시간 전송, 생 PCM 이어 붙여 재생
- WebSocket 연결 관리: 열기·끊김·재연결
- **세션 수명 관리** — 공식 문서 기준 음성 전용 세션은 압축 없이 **15분**, 연결은 약 **10분** 제한이다.
  회화실 관람은 이보다 길다. `GoAway` 신호 처리, `contextWindowCompression`(슬라이딩 윈도우),
  `sessionResumption`(핸들, 종료 후 2시간 유효)이 필요하다. 지금 스파이크에는 하나도 없다.

서버 쪽(BE1)에도 WebSocket 엔드포인트, 여러 관람객 동시 접속, 작품 변경 처리가 새로 필요하다.

## 판단과 제안

**측정값은 Live가 유리하다.** 실기기에서 1.5초 vs 8초, 사실 정확도도 Live가 높았다(BE1 채점 10/0/0).
8초는 관람객이 기다리기 어려운 시간이고, [응답 시간 측정](../../archive/docs/FE1/FE1_응답시간_측정.md)에서 확인한 대로
**보내는 양을 줄이는 방향으로는 줄일 수 없다.** 모델이 생각하는 시간이기 때문이다.

다만 전환 비용이 작지 않고, 12/1 시연까지 남은 기간에 세션 수명 관리까지 새로 만드는 부담이 있다.
제안하는 순서는 이렇다.

1. ~~아이폰에서 AudioWorklet 전송과 생 PCM 재생 확인~~ → **11/11 완료. 된다.**
2. BE1과 중계 형식을 `docs/api.md`에 적고, 세션 수명 관리(10분·15분 제한)를 나눠 맡는다.
   스파이크의 재연결은 2분 비활성 종료에서만 확인했다.
3. 여러 관람객 동시 접속, 작품 변경(다른 작품으로 이동), 인증을 정한다. 스파이크에 없다.
4. 그동안 현재 `/api/ask` 경로는 유지한다. 시연 대비 안전망이고, 지금 동작한다.

**개인정보 쪽은 Live가 오히려 낫다.** 브라우저 STT(`static/stt.js`)는 소리를 Apple·Google 받아쓰기
서버로 보낸다. 우리가 통제할 수 없는 경로다. Live는 우리 키로 Gemini에 보내므로 이미 쓰는 경로이고,
`AGENTS.md`의 "처리에만 사용하고 저장하지 않는다"를 우리 코드로 지킬 수 있다.

## 아이폰 실기기 결과 (2026-11-11)

도혁 님 아이폰 Safari에서 `/live` 페이지로 확인했다. **갈림길 두 개는 통과했다.**

**L01~L10 전부 통과했다.**

| 항목 | 결과 |
| --- | --- |
| L02 마이크 | 48000 Hz → 16kHz 변환 동작 |
| L03 생 PCM 24kHz 재생 | 통과. 시험음이 들렸다 |
| L04 받아쓰기 | 통과. 정확했다 |
| L05 답변 음성 | 통과. 끊김·튐 없음 |
| **L06 말 끝난 뒤 첫 소리** | **1,457 ms** (실기기·실제 망) |
| L07 말 끊기 | 통과. 재생이 즉시 멈춘다 |
| L08 질문 여러 번 | 1차 실패 → 중계 수정 후 통과 |
| L09 긴 공백 뒤 질문 | 1차 실패(2분 뒤 code 1006) → 재연결 구현 후 통과. 대화 내용도 유지됨 |
| L10 엉뚱한 작품 | 통과. 자료에 없다고 답한다 |

**AudioWorklet 마이크 전송과 생 PCM 재생이 아이폰에서 된다.** 이것이 Live 전환의 전제였다.

실기기 1,457 ms는 맥 중계(950~1,100 ms)보다 300~500 ms 느리다. 폰 처리와 실제 망 구간이다.
현재 `/api/ask` 경로의 7,945 ms와 비교하면 **약 5.5배 빠르다.**

### 실기기에서만 드러난 결함 두 개

맥에서 한 번씩만 시험했을 때는 둘 다 통과했다. 실기기에서 여러 턴·긴 공백으로 써 보니 드러났다.

**① 두 번째 질문부터 답이 오지 않음.** SDK의 `session.receive()`는 한 턴이 끝나면 스스로 종료된다
(소스에 `turn_complete`에서 `break`). 중계가 그것을 한 번만 돌려서, 1턴 뒤로는 아무도 Gemini
소켓을 읽지 않았다. 그래서 답이 오지 않고 20초 뒤 `keepalive ping timeout`으로 연결이 끊겼다.
턴마다 다시 호출하게 고쳤다. **한 턴만 시험하면 통과하는 결함이었다.**

함께 고친 것: 누르고 말하기 방식에서는 자동 음성 감지를 끄고 `activityStart`·`activityEnd`로
말의 경계를 알려야 한다(공식 문서). 그 모드에서는 `audioStreamEnd`를 보내지 않는다. 처음에는
둘을 섞어 써서 첫 턴만 우연히 동작했다.

**② 질문 사이 2분이 지나면 세션이 닫힘.** Gemini가 `1008 Session closed due to client inactivity`
로 세션을 닫는다. 버튼을 누를 때만 소리를 보내므로 질문 사이에는 입력이 전혀 없기 때문이다.
폰에는 WebSocket이 code 1006으로 끊긴 것처럼 보인다.

소리를 계속 보내면(침묵까지) 끊기지 않지만 **관람 내내 마이크 소리를 전부 올리게 되므로** 택하지
않았다. `AGENTS.md`의 "음성은 처리에만 사용"과 맞지 않고, 입력 음성 요금도 질문당이 아니라
관람 시간 전체에 붙는다(30분이면 약 200원. 질문 10번이면 약 60원). 대신 세션이 닫히면
**재개 핸들로 다시 붙는다.** 음성 전용 15분·연결 약 10분 제한에도 같은 처리가 필요하다.

맥에서 재연결을 확인했다: 170초 공백 → 120초에 세션 닫힘 → 130초에 재연결 → 다음 질문 630 ms.

**대화 내용도 유지된다.** "Who painted this?"로 물은 뒤 140초 쉬고(그 사이 재연결) "Tell me more
about him."이라고 물었더니 김홍도 이야기로 이어서 답했다. 재개 핸들이 맥락을 살린다는 뜻이다.

## 세션 수명 처리 (2026-11-14)

공식 문서([session management](https://aistudio.google.com/docs/live-api/session-management),
2026-11-14 확인)가 말하는 제한은 셋이다.

| 제한 | 문서가 적은 값 | 중계가 하는 일 |
| --- | --- | --- |
| 음성 전용 세션 | 압축 없이 **15분**. `contextWindowCompression`을 켜면 "무제한" | 압축을 기본값(`SlidingWindow()`)으로 켜 둔다 |
| 연결 하나 | **약 10분**. 연결이 끝나면 세션도 끝난다 | 재개 핸들로 세션을 여러 연결에 걸쳐 잇는다 |
| 종료 예고 | 연결이 닫히기 전에 `GoAway`가 `timeLeft`와 함께 온다. **얼마나 미리 오는지는 문서에 없다** | 받는 즉시 옮긴다. 남은 시간을 믿고 기다리지 않는다 |
| 재개 핸들 | 마지막 세션 종료 뒤 **2시간** 유효 | 핸들로 연달아 3번 실패하면 버리고 새 대화로 살린다 |

압축의 `trigger_tokens`·`target_tokens`는 비워 두고 서버 기본값에 맡겼다. 문서 예시가 기본값만
쓰고 권장값을 주지 않으며, 우리가 측정한 값도 없다. 긴 관람에서 앞 대화를 잊는 것이 문제가 되면
그때 측정해서 정한다.

고친 것 넷(`tools/live_relay_spike.py`):

1. **`GoAway`를 받으면 우리가 먼저 새 연결로 옮긴다.** 전에는 예고를 받고도 같은 연결을 계속
   읽었다. 그러면 연결이 `ABORTED`로 끊기고 그 턴의 답이 잘린다.
2. **답변 도중에 예고가 오면 그 답을 끝까지 내보낸 뒤 옮긴다.**
3. **연결이 답변 도중에 끊기면 폰에 `turn_complete`를 보낸다.** 전에는 폰이 답을 끝없이 기다려
   말하기 버튼이 잠긴 채로 남았다. 폰 쪽도 `reconnecting` 동안 버튼을 잠그게 맞췄다
   (`static/live_test.js`. 인터페이스 문서에는 적혀 있었지만 구현에 빠져 있었다).
4. **관람객이 창을 닫으면 Gemini 세션도 바로 닫는다.** 전에는 폰 쪽 루프만 끝나고 중계가
   남아서, 떠난 관람객의 세션을 자기 수명까지 붙들고 재연결을 계속했다.

확인한 방법: `tests/test_live_session_lifetime.py`. Gemini 자리에 대본대로 움직이는 가짜를 놓고
여섯 가지 상황(비어 있을 때 예고, 답변 중 예고, 답변 중 끊김, 2분 비활성, 핸들 거부, 되돌릴 수
없는 핸들 업데이트)에서 중계가 무엇을 하는지 봤다. 여섯 가지 모두 통과했다. 실제 Gemini로는
`tools/fake_browser_live.py`로 2턴을 확인했다(압축을 켠 상태, 말 끝난 뒤 첫 음성 699·794 ms,
한 연결에서 두 턴 모두 성공).

**가짜로 한 시험이므로 다음은 확인하지 못했다.** 10분·15분에 실제로 걸렸을 때 이 처리가
넘어가는지, 압축이 실제로 15분 제한을 없애는지, 압축 뒤에도 앞 대화를 기억하는지, 실제 `GoAway`가
종료 몇 초 전에 오는지는 **실기기에서 10분 넘는 연결로 확인해야 한다.**

## 남은 확인 사항

- **10분 넘는 연결을 아이폰에서 확인한다.** 위 세션 수명 처리의 실기기 확인이 여기에 걸려 있다.
  지금 실제로 확인한 것은 2분 비활성 종료뿐이다.
- 아이폰에서 L09(긴 공백 뒤 재연결)를 다시 확인한다. 맥에서만 확인했다.
- 재생 Hz 값을 기록하지 못했다(마이크는 48000 Hz로 확인). 다음 시험에서 적는다.
- 압축이 도는 긴 대화에서 답변 품질이 떨어지지 않는지 본다(BE1과 함께).
