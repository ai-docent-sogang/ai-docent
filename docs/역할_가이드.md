## 공통: 모두 알아야 할 것

우리는 12/1까지 스마트폰 웹앱 도슨트를 만듭니다. 외국인 관람객이 조선 회화를 손가락으로 가리키고 말하면, 작품을 알아보고 관람객이 아는 외국 그림과 비교해 영어로 답합니다.

### 11/4 결정

- 웹앱을 먼저 만들고, 글라스는 나중에 연결할 수 있게 `/api/turn`을 기기와 무관하게 유지합니다.
- 작품 인식은 YOLO 탐지, 프레임 추적, 임베딩 벡터 검색으로 합니다. 임베딩 모델은 기업이 지원합니다.
- 손가락 가리키기(MediaPipe)는 폰 브라우저에서, 나머지 인식은 서버에서 처리합니다.
- STT·TTS는 11/11까지 비교해 고르고, 목소리와 발화 방식은 FE3가 기준을 정합니다.
- 팀장은 FE1이 겸합니다. 대화 원문·음성·사진은 저장하지 않고, 질문 유형은 라벨만 기록합니다.

### 학습에 대한 원칙 (11/4 점검)

모델을 실제로 학습시키는 일은 작품 인식 보강(BE2) 하나뿐입니다. 작품 설명과 외국 작품은 Gemini를 학습시키지 않고, 검증된 CSV 내용을 매번 함께 보내 그 안의 사실만 말하게 합니다. 비교작 선택과 질문 유형 분류도 학습 없이 규칙과 라벨로 합니다. 근거는 [AI 도슨트 학습 영역 점검](https://claude.ai/artifact/XvDVXAYHL93BKjTY7n6wtX)에 있습니다.

### 대화 한 번의 흐름과 담당

1. 관람객이 작품을 손가락으로 가리킴 — MediaPipe, 폰 (FE2)
2. 녹음, 여러 프레임, 가리킨 좌표를 모음 — `app.js`·`audio.js` (FE1), `pointing.js` (FE2)
3. 서버로 전송 — `api.js` (FE1) → `server/app.py` (BE1)
4. 작품 인식: YOLO → 추적 → 가리킨 영역 → 벡터 검색 → `artwork_id` 또는 `unknown` — `recognition.py` (BE2)
5. 세션·작품 정보·비교 후보 꺼내기 — `session.py` (BE1), `content.py` (BE2), `data/` (FE3)
6. STT와 Gemini 답변 생성 — `gemini_client.py`·`prompts.py` (BE1)
7. 응답 반환과 로그 기록 — `app.py`·`logs.py` (BE1)
8. TTS로 읽어 주기 (FE1, 발화 기준 FE3), 자막·작품 카드 표시 (FE2)

### 협업 규칙

- 브랜치는 `이름/작업내용`, 메인에 직접 올리지 않습니다. PR은 한 명이 읽고 합칩니다.
- 매일 10분 공유를 하고, 막힌 지 2시간이 넘으면 바로 알립니다.
- 매주 금요일에 실제 아이폰으로 처음부터 끝까지 통합 시연을 합니다.
- AI 코딩 도구는 써도 되지만, 이해하지 못한 코드는 PR에 올리지 않습니다.
- Gemini API 키는 `.env`에만 둡니다. 관람객 얼굴이 찍힌 사진은 GitHub에 올리지 않습니다.

### 일정이 밀릴 때 줄이는 순서

1. 프레임 추적 → 한 프레임 + 가리키기로 대체
2. Live API 비교 → 요청-응답 방식 유지
3. 운영 페이지 → 대시보드 탭만
4. 비교쌍 → 20개에서 15개로

결정은 금요일 통합 시연에서 FE1(팀장)이 내립니다.

### 아직 정해지지 않은 것

- 각 역할의 담당자 이름
- 기업 임베딩 모델의 제공 시점과 형태(API인지 모델 파일인지)
- STT·TTS 최종 선택(11/11)
- 한 손으로 폰을 들고 다른 손으로 가리키는 자세가 자연스러운지
- 박물관의 국적 집계 허용 여부, 답하지 못한 질문의 텍스트 저장 여부

## BE2 — 인식

관람객이 가리킨 그림을 정확히 알아보고, 확실하지 않으면 `unknown`을 돌려줍니다. 그림을 잘못 알아보면 아무리 좋은 설명도 틀린 설명이 됩니다.

**인식 순서** 프레임에서 YOLO로 작품 영역 찾기 → 가리킨 좌표에 가장 가까운 영역 고르기 → 그 영역을 임베딩해 참조 이미지와 비교 → 여러 프레임에서 같은 후보가 이어지면 확정, 상위 후보 점수 차가 작으면 `unknown`
