# Live API 전환 검토 — 코드로 확인한 부분 (FE1, 2026-11-11)

담당: FE1 김도혁. 측정 도구: [`tools/probe_live_audio.py`](../tools/probe_live_audio.py),
[`tools/live_relay_spike.py`](../tools/live_relay_spike.py), [`tools/fake_browser_live.py`](../tools/fake_browser_live.py).
배경: BE1의 방식 비교 PR #7, FE1의 [응답 시간 측정](FE1_응답시간_측정.md).

## 왜 확인했나

BE1이 Live API로 첫 응답 0.8초(요청-응답은 8.1초), 사실 정확도 10/0/0을 측정하고 "Live 전환 여부는
FE1 음성 처리 작업량과 함께 결정해야 한다"고 남겼다. 다만 BE1의 실험은 질문을 **텍스트**로 보냈다.
FE1에게 중요한 것은 **음성을 넣었을 때**도 되는지, 그리고 폰 브라우저에서 그 경로를 쓸 수 있는지다.
실기기 없이 코드로 확인할 수 있는 것부터 확인했다.

## 확인한 것 ①: Live가 음성을 듣고, 우리 자료로 답한다

합성 음성("Who painted this, and why is the boy crying?")을 16kHz PCM으로 만들어 Live에 보냈다.
실제 관람객 음성을 쓰거나 저장하지 않으려고 맥의 `say`로 만든 소리를 썼다.

| 항목 | 결과 |
| --- | --- |
| 들은 질문 | "Who painted this and why is the boy crying?" — 정확 |
| 답변 | `key_facts`의 회초리·암송 평가 해석을 박물관 해석이라는 단서와 함께 말함 |
| 첫 음성까지 | 1,260 ms |
| 출력 형식 | `audio/pcm;rate=24000` (공식 문서와 일치) |
| 연결 시간 | 2,039 ms (관람 시작 때 한 번만) |

**DB를 거친다.** 작품의 `key_facts`를 시스템 지시문에 넣고 `ASK_INSTRUCTION`을 그대로 썼다.
BE1이 측정한 정확도 10/0/0도 같은 방식이었으므로, Live로 바꿔도 콘텐츠 DB 근거는 유지된다.

엉뚱한 질문을 걸러내는 것도 확인했다. 같은 음성을 **인왕제색도**에 대고 보냈더니 "우는 아이는
이 그림에 없고 자료에도 없다"고 답하고 다른 볼거리를 권했다. 지어내지 않았다.

## 확인한 것 ②: 폰 → 우리 서버 → Gemini 중계가 동작한다

`AGENTS.md`는 클라이언트 코드에 API 키를 넣는 것을 금지한다. 따라서 **폰 브라우저가 Gemini Live에
직접 붙을 수 없고**, 우리 서버가 WebSocket으로 가운데서 음성을 넘겨야 한다. 이게 Live 전환의
가장 큰 구조 변화다. `/api/ask`·`/api/turn`은 요청 한 번에 응답 한 번이지만, Live는 연결을 열어 둔다.

가장 작은 중계 서버를 만들고, 폰처럼 100ms씩 실시간으로 음성을 올리는 가짜 브라우저로 시험했다.

| 항목 | 결과 |
| --- | --- |
| 경로 | 가짜 브라우저 → 우리 서버(WebSocket) → Gemini Live → 서버 → 브라우저 |
| **말이 끝난 뒤 첫 음성까지** | **950 ms** |
| 답변 음성 길이 | 13.7초 (24kHz PCM 658 KB) |
| 받아쓰기 | 정확 |

`/api/ask`의 7,945 ms와 비교하면 **8배 빠르다.** 실시간으로 보내면 모델이 들으면서 처리하므로
텍스트로 보낼 때(1,260 ms)보다도 빨랐다.

## 확인하지 못한 것 — 실기기가 필요하다

아래는 코드로 알 수 없다. 아이폰 Safari에서 직접 해 봐야 한다.

- **마이크를 16kHz PCM으로 실시간 뽑기.** 지금 `static/audio.js`는 녹음이 끝난 뒤 한 번에 WAV로
  바꾼다(`OfflineAudioContext`). Live는 말하는 동안 계속 보내야 하므로 `AudioWorklet`이 필요하다.
  Safari가 지원하지만 우리 코드로 해 본 적이 없다.
- **24kHz PCM 재생.** 받은 소리는 WAV 파일이 아니라 생 PCM 조각이다. `AudioContext`로 이어 붙여
  끊김 없이 재생해야 한다. Safari의 자동 재생 제약(사용자 조작 안에서 시작해야 함)은 이미
  `initAudio()`로 겪은 문제이고, Live에서도 같은 제약이 걸린다.
- **에코.** 스피커로 답변이 나오는 동안 마이크가 그 소리를 다시 듣는다. 이어폰을 쓰면 줄지만
  기기와 함께 확인해야 한다. 지금 흐름은 버튼을 누를 때 답변 음성을 끊어서 피하고 있다.
- **기관 Wi-Fi에서 WebSocket 연결 유지.** 끊김과 재연결은 실제 망에서만 확인된다.

## 작업량 — 솔직하게

Live로 가면 FE1 쪽은 줄지 않고 **바뀐다.** 브라우저 STT·TTS(`static/stt.js`, `audio.js`의 `speak`)는
필요 없어지지만, 그 자리에 다음이 들어온다.

- `AudioWorklet`으로 마이크 실시간 전송, 생 PCM 이어 붙여 재생
- WebSocket 연결 관리: 열기·끊김·재연결
- **세션 수명 관리** — 공식 문서 기준 음성 전용 세션은 압축 없이 **15분**, 연결은 약 **10분** 제한이다.
  회화실 관람은 이보다 길다. `GoAway` 신호 처리, `contextWindowCompression`(슬라이딩 윈도우),
  `sessionResumption`(핸들, 종료 후 2시간 유효)이 필요하다. 지금 스파이크에는 하나도 없다.

서버 쪽(BE1)에도 WebSocket 엔드포인트, 여러 관람객 동시 접속, 작품 변경 처리가 새로 필요하다.

## 판단과 제안

**측정값은 Live가 유리하다.** 8초 vs 1초, 사실 정확도도 Live가 높았다(BE1 채점 10/0/0).
8초는 관람객이 기다리기 어려운 시간이고, [응답 시간 측정](FE1_응답시간_측정.md)에서 확인한 대로
**보내는 양을 줄이는 방향으로는 줄일 수 없다.** 모델이 생각하는 시간이기 때문이다.

다만 전환 비용이 작지 않고, 12/1 시연까지 남은 기간에 세션 수명 관리까지 새로 만드는 부담이 있다.
제안하는 순서는 이렇다.

1. 아이폰 Safari에서 `AudioWorklet` 마이크 전송과 생 PCM 재생만 먼저 확인한다(작품 1점, 중계 스파이크
   그대로). 여기서 막히면 Live 전환은 성립하지 않으므로 더 들어가기 전에 확인한다.
2. 되면 BE1과 중계 형식을 `docs/api.md`에 적고 세션 수명 관리를 나눠 맡는다.
3. 그동안 현재 `/api/ask` 경로는 유지한다. 시연 대비 안전망이고, 지금 동작한다.

**개인정보 쪽은 Live가 오히려 낫다.** 브라우저 STT(`static/stt.js`)는 소리를 Apple·Google 받아쓰기
서버로 보낸다. 우리가 통제할 수 없는 경로다. Live는 우리 키로 Gemini에 보내므로 이미 쓰는 경로이고,
`AGENTS.md`의 "처리에만 사용하고 저장하지 않는다"를 우리 코드로 지킬 수 있다.

## 확인하지 않은 것

**요금.** Live 음성은 텍스트보다 비쌀 것으로 보지만 단가를 확인하지 않았다. 전환을 결정하기 전에
공식 요금표로 확인해야 한다. "확인 필요"로 남긴다.
